Workflow Lifecycle

How a Request Navigates the Gateway

Incoming HTTP traffic enters Starlette middleware, validates atomic token allowances in Redis, leverages single-flight mutex caching for database reads, and dispatches background tasks.

1
Starlette Interception & IP Extraction
RateLimitMiddleware inspects request path (skipping /config, /docs) and retrieves client IP via IPKeyExtractor.
2
Atomic Lua Token Bucket Invariant
Executes token_bucket.lua in Redis. If tokens < cost, immediately aborts with 429 Too Many Requests and Retry-After. Zero race conditions.
3
Cache-Aside with Mutex & SWR Background Refresh
On GET /api/items/{id}, stale data is immediately served in ~1.5ms while leader coroutine acquires lock and triggers non-blocking refresh.
4
Decoupled Job Dispatching & Final Headers
Async jobs are pushed to queue:tasks via LPUSH (sub-2ms). The response delivers with X-RateLimit-Limit and X-RateLimit-Remaining headers.

Core Algorithm

Why the Token Bucket is Supreme

Token Bucket stores only 2 numbers in a Redis Hash: tokens and last_refill (O(1) memory). Refill is calculated mathematically on demand.

src/scripts/token_bucket.lua 
-- Continuous mathematical refill
local elapsed = now - last_refill
tokens = math.min(capacity, tokens + elapsed * refill_rate)

if tokens >= cost then
    tokens = tokens - cost
    redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
    redis.call('EXPIRE', key, math.ceil(capacity / refill_rate) + 60)
    return {1, math.floor(tokens), 0}  -- ALLOWED
else
    local retry_after = (cost - tokens) / refill_rate
    redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
    redis.call('EXPIRE', key, math.ceil(capacity / refill_rate) + 60)
    return {0, 0, tostring(retry_after)} -- REJECTED 429
end
Critical Failure Mode

The Race Condition Trap

Why Python read-modify-write causes double allowance under concurrency:

Naive Python:
Two requests read tokens = 1 at the same microsecond. Both deduct and overwrite tokens = 0. Result: 2 requests served when only 1 allowed.
Redis Lua Defense:
Redis executes scripts in a single-threaded loop. No command can interleave. Check, deduction, and write happen as one atomic unit.
Cache Protection Suite

3 Classic Disasters & Defenses

1. Cache Stampede (Thundering Herd)

50 concurrent requests for an uncached item. Only 1 leader acquires SET lock:{key} token NX PX 5000 and queries the DB. All others poll Redis. DB queries: 1.

2. Cache Avalanche

Randomized TTL jitter (±5s) desynchronizes simultaneous key expirations.

3. Cache Penetration

Negative caching with a 15s null envelope blocks repeat scans of non-existent IDs.

Stale-While-Revalidate (SWR)

Sub-2ms Stale Reads

When time.time() > expires_at, the client immediately receives cached data in ~1.5ms while a background task refreshes the database.

Producer-Consumer Architecture

JobDispatcher (Producer)

Creates UUID job_id, saves state in Redis Hash job:{uuid}, and pushes to queue:tasks via LPUSH.

JobWorker (Consumer)

Pops via BRPOP, sets status to processing, dispatches handler, and stores result or caught traceback.

Resilience

Worker Exception Isolation

Unhandled handler exceptions are caught in a try/except block, serialized into the error field of the Redis Hash, and marked status: failed without stopping the worker daemon.
