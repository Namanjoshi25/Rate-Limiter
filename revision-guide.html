Rate Limiter & Gateway Microservice

A complete mental model and architectural revision covering the Token Bucket rate limiter, Stampede-Proof Mutex Cache (with Stale-While-Revalidate), and the Decoupled Background Task Queue.

🎯 The Goal of This Microservice
To build a production-grade API gateway and caching layer in front of our backend that solves the 3 most dangerous database and API failure modes: saturation via traffic bursts (Rate Limiting), database collapse via cache misses (Stampede-Proof Mutex Cache), and slow write latency blocking the client (Decoupled Background Queue).
🚀 End-to-End Request Lifecycle Map

Follow what happens under the hood when a client makes an HTTP request to our service:

1
Client HTTP Request Arrives Middleware Layer

Request reaches RateLimitMiddleware in src/middleware.py. The client IP is extracted via IPKeyExtractor (inspecting client host or X-Forwarded-For).

2
Atomic Token Bucket Check in Redis Single Lua Script

FastAPI calls src/scripts/token_bucket.lua in Redis. Lua computes elapsed time, refills tokens up to capacity, and deducts cost atomically. If tokens < cost, immediately aborts with 429 Too Many Requests and Retry-After header.

3
Cache Lookup & Mutex Protection (GET /api/items/{id}) Stampede-Proof Mutex

The route calls MutexCache.get_or_compute() in src/cache/mutex_cache.py. If cached and fresh, returns in ~1-2ms. If stale, immediately serves cached data and dispatches background refresh. If empty (hard miss), only 1 leader coroutine queries DB via SET NX PX mutex; all 49 concurrent followers poll Redis.

4
Asynchronous Background Task Offload Sub-2ms 202 Accepted

For heavy jobs (emails, reports), the API calls JobDispatcher.enqueue_job() in src/queue/job_dispatcher.py. Job metadata is saved to Redis Hash job:{uuid} and pushed to queue:tasks via LPUSH. The decoupled JobWorker consumes it via BRPOP.

5
Headers Appended & Response Returned 200 OK

RateLimitMiddleware attaches X-RateLimit-Limit and X-RateLimit-Remaining headers to the response and delivers it back to the client.

📐 Token Bucket Mathematical Model

Instead of tracking sliding timestamp windows (which consume O(N) memory in Redis Sorted Sets), the Token Bucket needs only 2 numbers:

  • tokens: Current float count of tokens remaining.
  • last_refill: Unix timestamp of the last calculation.
Mathematical Invariant Refill on Demand 
-- 1. Compute elapsed time since last request
elapsed = now - last_refill

-- 2. Add refilled tokens, capped at capacity
tokens = math.min(capacity, tokens + (elapsed * refill_rate))

-- 3. If tokens >= cost: deduct & allow. Else reject.
if tokens >= cost then
    tokens = tokens - cost
    allowed = true
else
    retry_after = (cost - tokens) / refill_rate
    allowed = false
end
⚠️ Why Python Read-Modify-Write Fails
If Python reads GET tokens, calculates the new tokens, and does SET tokens, two concurrent requests will read the same balance, overwrite each other, and allow double traffic! Executing in Lua ensures 100% atomicity because Redis is single-threaded.

🔍 Annotated Code: src/scripts/token_bucket.lua
src/scripts/token_bucket.lua Redis Lua Execution 
local key         = KEYS[1]
local capacity    = tonumber(ARGV[1])
local refill_rate = tonumber(ARGV[2])
local cost        = tonumber(ARGV[3])
local now         = tonumber(ARGV[4])

-- Read existing balance and last refill time from Redis Hash
local data        = redis.call('HMGET', key, 'tokens', 'last_refill')
local tokens      = tonumber(data[1])
local last_refill = tonumber(data[2])

-- Initialize brand new bucket if key does not exist yet
if tokens == nil then tokens = capacity end
if last_refill == nil then last_refill = now end

-- Continuous mathematical refill
local elapsed = now - last_refill
tokens = math.min(capacity, tokens + elapsed * refill_rate)

if tokens >= cost then
    tokens = tokens - cost
    redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
    redis.call('EXPIRE', key, math.ceil(capacity / refill_rate) + 60)
    return {1, math.floor(tokens), 0}  -- {allowed=1, remaining, retry_after=0}
else
    local retry_after = (cost - tokens) / refill_rate
    redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
    redis.call('EXPIRE', key, math.ceil(capacity / refill_rate) + 60)
    return {0, 0, tostring(retry_after)}  -- {allowed=0, remaining=0, retry_after}
end
🌪️ The 3 Classic Cache Disasters

A naive cache setup collapses in production under real-world traffic:

1. Cache Stampede (Thundering Herd):
When a hot key expires, 1,000 concurrent requests miss simultaneously. All 1,000 hammer the database at once, taking the DB down.
Our Solution: Distributed Mutex Lock (SET NX PX). Exactly 1 request queries the DB; the other 999 poll Redis.
2. Cache Avalanche:
100,000 keys are cached with the exact same 60s TTL. Exactly 60s later, all 100,000 expire at the identical second.
Our Solution: TTL Jitter (+- 10% random offset), desynchronizing expiry waves.
3. Cache Penetration:
An attacker queries non-existent IDs (e.g. /items/-99999). The cache never stores nulls, so every request bypasses Redis straight to the DB.
Our Solution: Negative Caching (Null-Object envelope with short 15s/30s TTL).
⚡ Stale-While-Revalidate (SWR) Optimization

In Step 3 of Milestone 10b, we added SWR to eliminate follower polling latency:

Data Envelope Structure Redis JSON Value 
{
  "data": { "id": "item_1", "price": 49.99 },
  "expires_at": 1730712345.67  -- Soft Expiration timestamp
}
-- Hard Redis TTL = jittered_ttl * 2
How SWR works:
  1. When time.time() > expires_at, the data is soft-expired, but still present in Redis.
  2. The reader immediately serves the stale data to the client in ~1.5ms (zero wait!).
  3. Simultaneously, the leader coroutine acquires the distributed mutex and spawns a background asyncio task: _background_refresh().
  4. The background task queries the DB, stores fresh data with a new envelope, and safely unlocks the mutex.
🔒 The "Lock Stealing" Bug & Safe Lua Unlock

What happens if Thread A acquires a lock with a 5-second timeout, but DB query takes 6 seconds? Thread A's lock auto-expires in Redis. Thread B now acquires the lock. Thread A finishes and runs DEL lock:item. Thread A just deleted Thread B's lock! Now Thread C can enter, destroying mutual exclusion.

Safe Lua Unlock in MutexCache Atomically Check Token Before DEL 
-- Only delete the lock key if the token matches our UUID
RELEASE_LOCK_LUA = """
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
"""
📦 Producer-Consumer Architecture

When an API receives a heavy workload (e.g. generating a PDF, sending batch emails, running AI embeddings), it must never block the HTTP request.

1. JobDispatcher (Producer) — Ingestion < 2ms
Generates a job_id (UUID). Saves job payload & metadata to Redis Hash job:<job_id>. Pushes ID onto queue:tasks via LPUSH. Immediately returns 202 Accepted with the job_id.
2. JobWorker (Consumer) — Non-blocking BRPOP
Runs in background loop. Uses BRPOP queue:tasks 1 to block without CPU spinning. Pops job, marks status as processing, dispatches registered handler, and stores result or error.

🛡️ Exception Isolation
If a handler raises an unhandled exception, JobWorker catches it in try/except, writes the traceback to error in the Redis Hash, marks status failed, and continues running to process the next job without crashing the worker process!

🚀 FastAPI Lifespan Integration (src/main.py)

In production FastAPI apps, we manage connection pools and microservice instances inside the modern @asynccontextmanager lifespan:

src/main.py Lifespan Architecture 
@asynccontextmanager
async def lifespan(app: FastAPI):
    client = get_redis_client()
    store = RedisStore(client)
    
    # Attach all 3 primitives to app.state
    app.state.limiter = RateLimiter(store=store, extractor=IPKeyExtractor(), config=config)
    app.state.cache = MutexCache(client)
    app.state.dispatcher = JobDispatcher(client)
    
    yield
    
    # Clean graceful teardown on server shutdown
    await client.close()
